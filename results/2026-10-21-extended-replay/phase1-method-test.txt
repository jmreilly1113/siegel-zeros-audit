Extended replay, Phase 1: measurement method and its test (COMPUTED unless marked INFERRED)

Peak memory method used: 111_memsample.py, run as root OUTSIDE the sandbox. It locates the transient unit's own unified cgroup
(user@1000.service/app.slice/run-uN.service) from the unit's main process, and every 0.5 s reads cgroup.procs and each
process's VmRSS and VmHWM. Recorded: peak_rss_sum_kb (sampled sum of VmRSS; lower bound of the true peak) and peak_hwm_kb
(largest single-process kernel high-water mark). No unit property is set; 67_corpus_run.sh is unchanged.
Why not the brief's first two options: kernel 5.15 has no memory.peak; systemd 255 has no MemoryPeak; in this hybrid cgroup
setup the unit's v1 memory cgroup is the whole user@1000.service (shared, includes page cache). /usr/bin/time -v outside the
wrapper would measure the systemd-run client, which is not the parent of the unit's processes, so it was not used.
Export: the same sampler opens the temp export file Comparator passes to nanoda, hashes it and (for the replay) copies it.
Build disk: du -sk of lean/.lake/build before and after the prebuild.
